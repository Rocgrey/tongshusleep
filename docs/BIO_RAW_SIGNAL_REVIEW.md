# BIO-7349 厂家测试截图与原始信号

## 本次资料结论

2026-11-11 检查用户提供的 BIO-7349 目录，共 7 张 JPG，没有 APK、TXT、JSON、CSV 或 Protobuf 二进制。因此本次依据截图判断功能和字段，不把截图转写成完整原始采样文件。

厂家 IWBle 1.30.0626 的实时数据页显示 `ProtoBufRealTimeData` 对象。现有厂家协议 `Protocols/Iwown/realtime_data.proto` 明确：16 (0x10)=ACC（加速度），512 (0x200)=BIOZ（生物电阻抗），2=PPG（光学脉搏波）。512 不是 PPG。工厂测试页也显示 gsensor、bioz 等检测项，但 OK 不证明整夜记录质量或采样覆盖。

实时数据数组具有原始信号性质；采样率、单位、轴顺序、通道数、时间戳编码仍需厂家确认。不能按 6 个值/包推断 6 Hz，也不能只凭 40 多个正负值自动拆分三轴。`ProtoBufRealTimeData` 是 Android SDK 对象名，网络发送格式还需检查。

更重要的是，睡眠截图已出现 2026-11-10 23:49 至 11 日 06:56 的真实厂家分期展示，包含 sleepMode 3/4/6/7，以及 completeFlag、datastatus、inSleepTime、outSleepTime 和 sleepdata。它说明厂家测试程序具备取得结果的路径；不能仅凭截图确定是本地 SDK 还是云算法。首页的时长汇总与分段列表还需原 JSON 复核，不能直接照搬成我们的统计结果。

使用截图中用户自己的实际 MAC（未写入代码或本文）重测公开算法账号，仍返回 10403（设备归属未确认），无 sections。此前旧日志设备哈希的失败不再是唯一证据，但仍不能据此说硬件不支持睡眠。需厂家核对算法账号、设备绑定，以及测试 App 实际调用方式。

## App 增量改动

- “设备数据接入”新增“下次连接采集原始信号”，默认关闭、单次生效。已确认 BIO 型号时，发送厂家协议的 ACC|BIOZ 位掩码，最多采集 10 秒后发送停止。中断/断连时尽力停止，未返回原始包不认定不支持。
- 每次最多 256 包/100000 个值，每包上限 4096。保留类型、设备原始秒数、包序号、数组和已验证 RtNotification 的原 Protobuf 内容。UInt32 原编码可通过 Base64 还原，有符号显示与 Android int 对齐。
- 接入报告新增类型选择、采样包数量和首包原值图，不把包内顺序伪装成秒，不推算深睡/REM。旧报告没有新字段时兼容解码。
- 数据先保存在本机接入报告与独立待传批次。按最多 100 包切分，稳定 upload_id/capture_id；断网、重启或新一轮采集后，旧待传批次仍保留。
- 登录且开启原有自动同步时通过自己的平台上传。成功回执按服务地址+用户 ID+批次隔离。原始数据入口与睡眠算法入口独立，接收原始信号不等于睡眠分析已经完成。

新增 `RawSensorData.swift`、`RawSensorReportView.swift`、`RawSensorTests.swift`，修改接入客户端/报告、设备视图和 App 同步层。原有本地睡眠、戒指、系统健康和体征不删除。

真机：先结束其他 App 的设备同步 → 在设备接入处开启“下次连接采集原始信号” → 重连 BIO → 保持前台 → 等待读取结束 → 打开“本次接入报告”检查原始包数量/类型。开启账号自动同步且服务已部署后，Web 同账号查看和下载原始包。

短时采集仅验证链路，不是整夜研究数据集。要自行开发睡眠分期算法，仍需要确认采样说明、连续整夜数据和可靠的对照分期，不能用“静止若干分钟”直接判定深睡或 REM。
