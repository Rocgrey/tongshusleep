## 结论

厂商公开协议确实定义了心跳间隔、光学脉搏波和三轴加速度等数据，比只有最终睡眠阶段的接口更适合研究自己的算法。但公开资料主要讲 4G 设备向服务器上传，不能据此确认用户每款手表、手环均支持这些数据，更不能认定可通过 iPhone 蓝牙直接取得。

补充设备名称后，已找到厂商公开的 2020 年 iOS 蓝牙 SDK，提供具体服务 UUID、基础读取与历史同步方法，可作为接入候选。继续坚持手机本地保存、直接蓝牙同步，需要核对这些设备是否兼容该 SDK；固件、设备信息中的正式型号及能力清单仍待实测或厂商确认。

## 有用的数据定义

| 数据 | 官方字段或示例 | 可以用于什么 | 当前边界 |
| --- | --- | --- | --- |
| 分钟健康记录 | `HisDataHealth`，含 `hr_data`、`bxoy_data`、`pedo_data` 等 | 心率、血氧、运动等已有结果的图表 | 不是连续波形；不同字段是否有值取决于型号 |
| 步数 | `HisHealthPedo.step`，实时汇总 `health.step` | 显示设备已计算的步数 | 分钟步数和当天累计需要分别处理，不能重复累加 |
| 心跳间隔 | `HisDataRRI.raw_data` | 清理后研究心跳变化及睡眠相关特征 | 需确认间隔来源、单位、有效性标记与整夜覆盖 |
| 光学脉搏波 | `HisDataPPG.raw_data` | 候选波形及睡眠特征研究 | 尚缺对应型号的通道、采样率、单位和采集条件确认 |
| 三轴加速度 | `HisACCelerometer.acc_x/acc_y/acc_z`、`acc_data_count` | 身体活动、自研计步、辅助区分睡眠与清醒 | 需确认采样率、量程、单位、完整性及同步时间 |
| 陀螺仪 | `HisGyroscope` | 可选运动补充信号 | 协议有定义不代表具体设备支持 |
| 心电 | `HisDataECG.raw_data`，另有多导联数据 | 支持型号上的心电信号研究 | 不能认为每款手表都有，也不是睡眠分期的必需输入 |
| 睡眠计算输入 | `HisHealthSleep.sleep_data` | 厂商睡眠算法输入的一部分 | 未公开每个值的完整语义，不能当作连续原始加速度 |
| 睡眠阶段结果 | 云端 `sections[].type` | 展示厂商计算的分期 | 3 深睡、4 浅睡、6 清醒、7 快速眼动；不是算法源码 |

HRV 协议还定义了不同统计字段，需要按正式说明确认单位和缩放，不能全部归并成同一个无单位的分数。协议中的血糖、血脂、尿酸等字段不会因本次资料核对自动重新加入 App。

## 示例代码实际提供什么

`SleepPreprocessor.java` 把分钟记录整理为时间、心率、运动、HRV、睡眠输入等结构。`CombineSleepRawData` 负责拼接记录，没有实现最终深睡、浅睡或快速眼动的分类算法。

`RriPreprocessor.java` 将每个 32 位数据拆为高、低两个有符号 16 位值。知识库《房颤散点图数据格式.docx》的可见预览说明该格式含按分钟分段的标记、格式头及缺失标记，间隔单位为毫秒。因此不能把数组中的所有正数直接当成有效间隔，必须先解析格式。

`AccPreprocessor.java`、`HistoryDataParser.java` 中提供三轴字节展开示例。但示例不代替正式规格：其中低字节符号处理等细节应另外核验；光学示例还包含取绝对值处理，不能未经确认直接作为原始波形重建依据。

知识库《睡眠计算公式.pdf》的可见预览使用入睡时间、总时长、深睡占比、清醒时长计算得分。它以已有分期为输入，不能反过来生成分期；与 App 自定义参考分也不能默认为同一算法。

## 两种接入方式对当前 App 的影响

1. **蓝牙直接读取**：符合当前本机存储目标。新发现的公开旧 SDK 已给出服务、特征与历史同步实现，可用于核对协议；仍需对应新型号的兼容性、认证和最新数据定义。
2. **4G 上传服务器**：公开资料和示例相对完整，可接收并解析支持型号上传的数据，然后由 App 获取。此路线需要服务器和设备上传地址配置，不能描述为仅靠当前 iPhone 本地功能即可完成。

厂商云睡眠接口 `/calculation/sleep` 需要账号权限，并接收前一天与当天的睡眠输入；文档说明心跳间隔输入用于计算快速眼动。调用它意味着向厂商服务发送数据，不符合当前默认只在手机保存的方式。需要询问是否提供可离线运行的睡眠算法 SDK。

公开协议还定义了加密数据类型；协议文件存在不代表已有认证、解密权限。是否需要绑定、联网激活或商业授权须按具体型号确认。

## 公开 iOS 蓝牙 SDK 的具体线索

`BLE_SDK_2020` 为 Swift 源码与演示工程，README 使用 CoreBluetooth 和 SwiftProtobuf。仓库根目录许可证为 BSD 3-Clause；若后续采用代码需保留相关声明。不能仅因公开下载就认定其包含当前型号全部权限或固件能力。

蓝牙定义来自 `Products/Protobuf/BLEProtobuf.swift`：

| 用途 | UUID |
| --- | --- |
| 服务 | `2E8C0001-2D91-5533-3117-59380A40AF8F` |
| 通知 | `2E8C0002-2D91-5533-3117-59380A40AF8F` |
| 写入 | `2E8C0003-2D91-5533-3117-59380A40AF8F` |

实际公开方法包括 `getDeviceInfo()`、`getBatteryInfo()`、`getRealTimeData()`、`getSyncDataIndexTable(type:)`、`getStartSync(type:blocks:)`。这些读取方法会生成需要发送给设备的协议请求，不能把蓝牙特征为“可写”误解成没有读取接口。

`DataParseProtobuf.swift` 的历史类型定义包含健康、定位、心电、脉搏波、心跳间隔、用药、血氧和游泳。旧版没有当前 4G 协议中的加速度类型，不宜直接照搬以支持所有新字段。README 与实现中的部分类型名称也存在版本差异，使用前需按源码核对并适配当前 Swift 工具链。

候选验证顺序为：分别扫描和记录服务；服务匹配时检查通知、读取设备信息和电量；再按支持的历史类型查询索引并获取实际存在的记录。先统计字段、单位和整夜覆盖，不把发现 UUID 或查询成功当成已取得原始信号。

目前没有把此 SDK 集成到安装版 App，也没有对三台设备完成以上验证。现有戒指协议与新 SDK 不同，蓝牙连接成功不会自动完成新型号适配。

## 自己写算法的可行性

- **计步**：如果能获取连续且单位明确的三轴加速度，可优先做研究版本，用人工计数及不同活动场景校验误计和漏计。只有厂商步数结果则只能展示结果，无法重算原始步数。
- **睡眠与清醒**：连续身体活动信号结合心率或心跳间隔，可做初步估算，但静卧清醒可能被误判为睡着。
- **深睡、浅睡、快速眼动**：需要连续、时间对齐、质量可检查的信号，以及有整夜睡眠检查对照结果的数据进行训练或验证。只有每分钟心率均值、总步数或一晚 HRV 汇总不足以保证可靠区分。
- 研究算法与厂商结果应分开标注来源、算法版本、覆盖时段及缺失数据，不覆盖原有设备结果。原始信号是否经过滤波、降采样或压缩也要确认。

## 发给厂家的资料请求

请按每款完整型号与固件提供：

1. iOS 蓝牙 SDK、接口文档、可运行 Demo，以及 Swift 或 Objective-C 支持情况。
2. 无需原配 App 登录、无需云端的认证和历史同步方式；如需开发授权或激活，请说明条件。
3. 能否读取整夜原始光学脉搏波、逐次心跳间隔、三轴加速度，以及每项的通道、单位、采样率、时间戳、质量与缺失标记。
4. 上述数据是否可以同时采集、是否保存在设备、保留多少天、能否次日蓝牙补传；持续采集对电量和存储的影响。
5. 每分钟睡眠输入数组每个元素的含义；是否提供本地睡眠算法 SDK，而非仅云端 API；授权是否允许自研算法。
6. 心率、血氧、体温、HRV、运动等结果的有效值、缩放及累计规则；提供一份脱敏的整夜真实样例。

先对每款设备建立实际数据清单，再决定接入范围。不能承诺读取协议定义的全部数据，也不能在没有设备实测前承诺自行准确分期。
