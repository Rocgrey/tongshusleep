## 用户规则

1. 手机号账号通过“注册手机号 + 事先绑定并验证的邮箱”找回密码，不使用短信；邮箱账号通过注册邮箱找回。手机号不是验证码接收地址。
2. 邮件只能发送给服务端已绑定且符合找回条件的邮箱，不能因用户在找回页输入一个新邮箱就修改账号、绑定邮箱或发送该账号的重置验证码。
3. 手机号账号没有已验证邮箱：仍记得密码的用户先登录并验证绑定邮箱；已经忘记密码则走人工身份核实流程。不要只凭一个手机号、用户自报邮箱、用户名或健康记录直接允许改密。不要宣称已有自动人工客服服务；实现管理工具时需真实管理员权限与审计。
4. 新注册邮箱仍可选，不强制手机号注册用户提供邮箱，不自动合并手机号/邮箱账号，全部数据归属继续使用原有稳定 user ID。
5. 旧邮箱账号可使用保存在该账号上的注册邮箱完成本次邮件验证和重置。旧手机号账号不能将历史上仅填写、从未验证过的邮箱直接标记为已验证；需先登录、核验当前密码并完成邮件绑定验证。
6. 邮箱比对沿用现有注册和唯一性规则，避免登录、注册、绑定、找回采用不同大小写规则；不擅自改变现存账号的标识或主键。

## 找回接口（iOS 预接入字段，请按此实现）

### POST /api/v1/auth/password-reset/request

无需 JWT，JSON 两种形式：

```json
{"phone":"13800001234","email":"bound@example.com"}
```

```json
{"email":"registered@example.com"}
```

有 phone 时必须同时匹配该手机号账号和其已验证绑定邮箱；没有 phone 时按已有邮箱账号找回。不能把提交邮箱覆盖为账号的新邮箱。输入格式错误返回 422。

返回 200：

```json
{
  "request_id":"不可预测的随机请求标识",
  "expires_at":1800000000,
  "retry_after":60,
  "message":"若账号与邮箱资料匹配，验证码将发送至对应邮箱，请留意收件箱和垃圾邮件。"
}
```

`expires_at` 为 UTC Unix 秒，实际取发送挑战创建时间后 10 分钟，不使用上方示例值。`retry_after` 为正整数秒。邮件为 6 位数字验证码，不返回验证码本身或任何登录 token。

对账号不存在、邮箱不匹配、无已验证找回邮箱、账号不可用，使用相同响应结构及条件性提示，不泄露账号是否存在、真实绑定邮箱或 user ID。请求标识必须不可推测；无资格请求绝不能通过 confirm。统一限流策略，避免利用响应内容、状态或明显时差枚举账号。

接入真实邮件投递（SMTP 或邮件 API）。没有配置或邮件服务整体不可用时返回 503，不能打印验证码代替真实邮件后声称功能完成；不能把“成功提交投递”当成已送达用户邮箱。

### POST /api/v1/auth/password-reset/confirm

无需 JWT，JSON：

```json
{"request_id":"上一步返回标识","code":"123456","new_password":"new-password"}
```

后端校验请求归属、验证码、有效期、尝试次数、账号当前状态和邮箱绑定是否仍有效。密码规则与当前注册保持一致：至少 6 个字符、不超过 72 字符及 72 UTF-8 字节。确认密码只由 UI 检查，不进接口；后端仍独立校验密码。

成功 200：

```json
{"message":"密码已更新，请使用新密码重新登录。"}
```

验证码错误、过期、已使用、挑战不合格返回 400 和统一 `{"detail":"验证码错误或已过期，请重新获取。"}`，不暴露账号详情。限流返回 429、格式错误 422；网络和业务错误沿用 FastAPI detail 结构。确认成功不发登录 JWT，不自动登录。

## 邮箱绑定及验证接口（需要同时完成）

### POST /api/v1/auth/email-verification/request

Bearer JWT，请求：

```json
{"email":"recovery@example.com","current_password":"current-password"}
```

身份取 JWT 的 user ID，重新校验当前密码。邮箱冲突、密码错误和频控使用明确业务提示，不把未验证邮箱直接写入已验证绑定。向新邮箱发送独立用途验证码；成功返回与找回 request 相同的 `request_id, expires_at, retry_after, message` 字段。

### POST /api/v1/auth/email-verification/confirm

Bearer JWT，请求：

```json
{"request_id":"绑定请求标识","code":"123456"}
```

核验当前 JWT 用户、绑定挑战归属和验证码后，才在事务中更新账号邮箱与验证状态。不能用其他用户挑战绑定。成功返回 200 `{"message":"邮箱已验证，可用于找回密码。"}`。

GET `/api/v1/auth/me` 兼容增加 `email_verified`（布尔）、`email_verified_at`（UTC 时间或 null）；原 id/username/phone/email/created_at 保持兼容。新增状态供后续 App“我的账号 → 找回邮箱”接入；不要改变现有注册、登录请求字段。

## 存储和鉴权

- 用兼容数据库迁移增加邮箱验证状态、验证码挑战及会话失效版本/时间等必要字段，保留全部原用户和健康数据，不删库、不统一重设密码、不把历史邮箱全部标为已验证。
- 验证码用安全随机数生成，仅保存带服务端密钥的 HMAC 等抗离线穷举的校验值。挑战区分 reset-password 和 verify-email，用途不能混用，绑定 user ID、邮箱、到期时间、失败次数、使用状态。不要在日志、错误、响应、Git 中记录密码、验证码或凭证。
- 每个挑战最多 5 次验证；同用途重新发送后撤销此前验证码；至少间隔 60 秒，按 IP、账号和邮箱限流，设置每小时及每日上限。将上限配置化并在说明中给出实际值。
- 重置改密与验证码消耗必须在同一事务完成；并发确认只能成功一次。绑定邮箱变化时撤销旧的找回挑战；验证码过期和次数耗尽后均不可复用。
- 密码继续使用现有安全哈希方式。密码重置成功后，该用户所有旧 JWT/会话应失效，含其他设备，不能只删除当前手机 token。可采用 token_version 或密码更改时间，但所有受保护接口必须统一验证；兼容已有 JWT 的升级规则写清楚。原密码失败，新密码能登录原 user ID。
- 已有正常注册、登录、退出、401 和账号隔离不回归。找回不会创建新用户或更改健康数据归属。

## Web 页面

在现有 Web 登录页加入“忘记密码”：手机号/邮箱账号切换、资料填写、发送验证码、冷却倒计时、验证码、新密码与确认密码、错误提示和成功后返回登录。按钮请求期间防重复点击，不把发送动作视为验证成功。
