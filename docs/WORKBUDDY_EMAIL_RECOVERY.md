## 一、用户流程

登录页增加“忘记密码”入口，用一个简洁页面完成：

**手机号／邮箱 → 获取验证码 → 输入验证码和新密码 → 确认重置 → 返回登录。**

- 手机号账号：向该账号的注册手机号发送短信验证码，不要求绑定或提供邮箱。
- 邮箱账号：向该账号的注册邮箱发送邮件验证码。
- 找回无需先登录，但必须通过对应联系方式的验证码验证。不能只填写账号就直接改密。
- 仅允许发送到服务端该账号已有的注册联系方式，不在找回流程中修改手机号、绑定新邮箱、创建新用户或合并账号。
- 新注册邮箱仍可选，原手机号账号及已有邮箱账号继续兼容。数据归属使用原有稳定 user ID。
- 本次不要求新增邮箱绑定页面或 email-verification 接口，不把邮箱绑定作为手机号找回的前置步骤。若已有相关能力，保持原有兼容即可。

## 二、接口契约

先检查现有代码和 OpenAPI，复用已有能力，避免重复建设。以下为拟定的新契约；若已有旧版“手机号 + 绑定邮箱”的实现，请明确提供与本契约的差异及兼容安排，不静默修改字段。

### POST /api/v1/auth/password-reset/request

无需 JWT。JSON 二选一，字段必须提供非空有效值；不允许同时提供 phone 和 email，也不能两者都不提供。

```json
{"phone":"13800001234"}
```

或：

```json
{"email":"user@example.com"}
```

手机号规范化沿用现有大陆手机号规则（可接受 +86 后转为现有存储格式）；邮箱比对沿用现有注册和登录规则，不擅自改变账号唯一性或历史标识。

成功返回 200：

```json
{
  "request_id":"不可预测的随机请求标识",
  "expires_at":1800000000,
  "retry_after":60,
  "message":"若账号存在，验证码将发送至对应手机号或邮箱。"
}
```

- `expires_at` 为 UTC Unix 秒，实际设置为本次挑战创建后 10 分钟，不使用示例中的固定值。
- `retry_after` 为正整数秒，默认 60；验证码为 6 位数字。
- 不在响应中返回验证码本身、用户 ID、真实账号状态或登录 token。
- 对账号不存在、账号不可用等情况，使用相同结构、状态和条件性提示；无资格请求绝不能通过 confirm，避免注册账号枚举。
- 必须接入真实短信和真实邮件投递。对应渠道未配置或整体不可用时返回 503；不能在控制台打印验证码或模拟投递后声称真实发送完成。提交投递不等于用户已收到。

### POST /api/v1/auth/password-reset/confirm

无需 JWT，请求：

```json
{"request_id":"上一步返回的标识","code":"123456","new_password":"new-password"}
```

后端根据 request_id 确定账号和接收渠道，独立校验验证码、有效期、尝试次数及账号当前状态，不接受客户端任意指定 user_id 或改密目标。注册联系方式发生变化时，旧挑战必须失效。

密码规则沿用现有注册：至少 6 个字符、不超过 72 个字符及 72 UTF-8 字节。确认密码只由 UI 检查，不进入接口；服务端仍独立校验新密码。

成功返回 200：

```json
{"message":"密码已更新，请使用新密码重新登录。"}
```

成功不返回登录 JWT、不自动登录。验证码错误、过期、已使用、次数耗尽或请求不合格统一返回 400 和 `{"detail":"验证码错误或已过期，请重新获取。"}`，不暴露账号详情。格式错误返回 422、限流 429、发送服务不可用 503，业务提示沿用 FastAPI detail 结构。

## 三、存储及登录凭证

- 验证码用安全随机数生成，仅保存带服务端密钥的 HMAC 等抗离线穷举的校验值，不明文保存，不在日志、错误、响应或 Git 中记录密码、验证码和密钥。
- 挑战绑定账号、接收地址、渠道、用途、到期时间、失败次数和使用状态。若已有其他验证码用途，不允许混用。
- 每个挑战最多验证 5 次；同账号同用途重发后旧码失效；至少间隔 60 秒。按 IP、账号和接收地址设置频率、每小时及每日上限，配置化并说明实际值。
- 密码更新和验证码消耗在同一事务完成；并发确认最多成功一次。过期、用过或次数耗尽的码不能复用。
- 密码继续使用现有安全哈希。重置后该账号全部旧 JWT／会话失效，包括其他设备，不是仅删除当前手机 token。可用 token_version 或改密时间，但所有受保护接口必须统一校验，说明已有 JWT 的兼容升级规则。
- 使用兼容数据库迁移保留全部用户和健康数据，不删库、不统一重置密码。新密码登录仍对应原 user ID，原密码失败，旧 JWT 返回 401。
- 保留正常注册、登录、退出、账号隔离和所有健康接口的行为。

## 四、Web 页面

在现有登录页加入“忘记密码”，支持手机号／邮箱切换，输入对应账号后获取验证码，再在同一页面填写验证码、新密码及确认密码。

提供重发倒计时、请求中的按钮禁用和加载状态、验证码与密码校验、清楚的错误提示。发送请求不等于验证成功；改密成功后返回登录。不新增无关的设置步骤，不修改现有信号、睡眠和步数页面。

## 五、真实服务配置及交付

1. 接入实际短信服务（例如腾讯云短信）和邮件服务（SMTP 或邮件 API）。通过部署环境变量保存凭证；短信列出服务账号、权限、应用 ID、签名、模板及所需审核，邮件列出发件账号、授权凭证、TLS 和发件域名配置。
2. 告知我需要申请哪些账号、短信签名和验证码模板，以及哪些配置尚未准备好。不要使用 App 内嵌密钥或把密钥提交到仓库。
3. 未配置真实渠道时明确列为阻塞，不把固定验证码、模拟短信／邮件或假投递当作真实联调成功。自动化测试可用明确标注的测试 transport，与真实收信验证分开报告。
4. 验证手机号无需邮箱和已有邮箱账号两条流程；未知账号、无效格式、同时传 phone/email、错误／过期／耗尽／重发旧码、并发复用、限流、发送失败和联系方式变化。
5. 验证改密后原密码失效、新密码登录、全部旧 JWT 401、稳定 user ID 不变、睡眠／步数／信号数据不丢失，现有登录注册及数据接口不回归。
6. 更新 OpenAPI、迁移、配置和测试说明，提交到 `Rocgrey/sleep_tongshu_web` 并部署。交付提交号、部署 HTTPS 地址、最终接口字段、短信／邮件配置状态和真实测试结果。
7. iOS 端由 App 开发方在 `Rocgrey/tongshusleep` 单独修改和联调；不要自行修改该仓库或声称已经更新了用户手机。
