# 穿戴设备日志核对结果

日期：2026-11-04。

本次离线检查用户提供的 SDK 日志、配置缓存、设备验证 JSON 和手表探测 JSON，并对照先前提供的 SDK 文档及厂家示例。没有执行日志里的命令，没有重新连接设备，也没有把日志导入正式健康记录。本文不包含账户、令牌、设备地址、个人测量值或原始蓝牙报文。

## 主要结论

| 设备 | 这批文件已证实的内容 | 自主算法还缺什么 |
| --- | --- | --- |
| HR802，固件 9.12.15 | 配套 App 日志已有健康记录，以及厂家计算好的浅睡、深睡、清醒、快速眼动 | 实际 iOS SDK；当前固件的原始信号支持、授权和完整返回格式 |
| L03 Ultra，固件 00.12.11 | 验证报告已有睡眠与体征结果 | 尚未证实能取得逐次心跳间隔、连续脉搏波、三轴加速度 |
| BIO 系列，本次回报型号 BIO9，固件 103.0.0.11 | 两次探测各收到 119 包健康数据和 7 包心跳间隔通道数据 | 完整间隔格式、缺失标记与时间规则，整夜覆盖和身体活动信号 |

BIO 心跳间隔通道是本次最明确的新线索，但当前证据不足以直接生成自主深睡、浅睡或快速眼动结果。另两款手表没有可在本批文件中独立确认的原始信号结果，不能从 BIO 的成功推定它们也支持。

## HR802：已有健康与睡眠结果，原始信号入口仍待确认

### 配置缓存

`.data` 是 Apple 二进制属性列表，采用 NSKeyedArchiver 存储。用属性列表解析器读取结构，不加载其中的归档对象为可执行类。

- `aboutModel.data`：软件版本 9.12.15，内部型号 H656_012，平台 RTL8762C，与用户提供固件一致。缓存中的通用设备字段不能都解释成戒指的实际硬件能力。
- `functionListModel.data`：`isSupportEmotion = 0`，`HRV = 0`。能力标志只说明该接口报告的状态，不能代替实际数据验证。
- `configModel.data`：包含自动心率检测间隔等设置。测量间隔不是逐次心跳间隔，也不是传感器采样率。
- 登录模型包含账户相关字段，与原始信号分析无关，未用于登录或联网调用。

### 实际健康与睡眠记录

`EveryDayLog/App_log_0/` 的健康 JSON 出现 `hr`、`spo2`、`btp`、`step`、`hrv`、`Pressure` 等字段，并有非零结果。字段单位、无效值和业务含义仍应按正式 SDK 定义确认；尤其不能仅凭 `Pressure` 这个名称认定它是血压。

实际存在非零 `hrv`，所以不能把某个 HRV 功能标志为 0 解释成设备完全没有 HRV 结果。单个 HRV 结果仍不能还原逐次心跳间隔。

`AppLog_Update/【SNSleepAlgorithmHelp V1V2V3】` 的 11 月 3、4 日日志明确写出：

| 日志阶段编号 | 日志给出的名称 |
| --- | --- |
| 1 | 浅睡 |
| 2 | 深睡 |
| 3 | 清醒 |
| 5 | 快速眼动 |

这是厂家流程输出的睡眠分期，不是原始加速度，也不是睡眠算法源码。相同夜晚被重复同步，不能按日志行数累加时长或清醒次数。未佩戴、关机、缺口和入睡前清醒也需要单独处理。

### 为什么还没有证实 PPI 可读取

PPI 指相邻脉搏的时间间隔。

- 三天日志共 37 次功能输出的 `isSupportEmotion` 均为 0。
- 情绪日志共 35 轮检查最近 7 天，245 个逐日检查项均显示 0 条。
- 这些“0 条”描述的是本地等待上传的 PPI 队列，不能当作对硬件原始数据接口的直接否定。
- iOS 文档第 24～26 页的 PPI 示例要求 `isSupportEmotion` 支持及 `.emo` 授权通过；本次观察到的固件状态不满足该示例的功能前提。
- 本批日志中未找到原始数据接收接口成功返回的证据，也未找到连续脉搏波或加速度样本。

因此，需要厂家确认当前固件是否开放 PPI、是否需要不同固件或开发授权。不能通过修改 App 中的功能开关就宣称设备已经支持。现有文件依然不是 `RingSDK.framework`、头文件或完整 Demo。

- 波形样本数为 0；没有收到被动波形回调，也没有运行未经确认适用于该型号的主动测量。
- 三轴运动接口未请求，原因是型号适用性尚未确认；这不等于证明硬件不支持。
- 已检查的字段清单中，心电、脉搏波和部分间隔数组为空。但字段清单有截断标记，不能外推到所有未检查内容。
- 分钟级步数、活动量或压力结果属于处理后的汇总，不能当作原始身体活动信号。

### 离线拆包结果

厂家 Java 示例 `RriPreprocessor.java` 将每个 32 位值先取高 16 位、再取低 16 位，均转为有符号数。本批 7 包共 247 个 32 位值，拆出 494 个有符号 16 位值。

知识库《房颤散点图数据格式.docx》的可见正文预览说明：`-3` 是分钟分段标记；包括它在内的前 5 个值是格式头；连续两个 `-6` 开始是格式尾；中间的负值表示缺失。本次只取得有限正文预览，不能当作完整协议。

按该规则进行初步结构检查：

- 7 包均找到格式头与连续两个 `-6` 的格式尾。
- 去掉格式头尾后的正文共有 392 个值：370 个正数候选间隔，22 个非正标记。
- 标记必须保留其位置；不能删除标记后把两侧间隔当成连续心跳，也不能把格式头里的正数算成间隔。
- 7 包时间戳从首包到末包跨 2417 秒，约 40 分钟；相邻时间戳差为 61、557、600、582、60、557 秒，并非连续整夜采集。

这些数量说明通道有实际内容，不代表 370 个值已经全部通过生理信号质量验证。本次没有据此计算 HRV、睡眠阶段或健康评分。还需完整格式确认时间含义、缺失长度、质量标志、有效间隔规则和适用固件。

目录显示有 38 条间隔记录，本次只收到 7 包；不能认定其余记录没有数据。需核对历史请求的序号边界、分页和结束标记，避免把同一批记录反复当作新增数据。
