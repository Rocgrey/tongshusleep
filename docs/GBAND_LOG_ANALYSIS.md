## 结论

**G Band 在这段日志中确实收到了设备响应和两轮分包数据。sleeptongshu 当前缺少对应的厂商认证、同步与解码流程，因此“可以连接”仍不等于“可以显示睡眠”。这次分析尚未修复戒指同步。**

日志中的 `A7` 功能包和 `B8` 开关包，与 Veepoo 公开 SDK 头文件描述的结构吻合。结合 G Band 的开发商信息，Veepoo SDK 是目前有依据的优先接入方向；这仍不等于已经验证该 SDK 对本批次戒指及固件的完整兼容性。

### 不能把原始字节直接当成睡眠指标

拼接每组序号 1、2 包的载荷后，可以观察到 `B1` 至 `C2` 范围内的若干“标签、长度、值”结构，以及末尾的零填充。某些字段在全部记录中均为零或 `FF`；另一些字段会变化。

这只能用于核对分包和字段边界。未取得这版协议的字段定义、无效值规则及单位前，不能把某个字节命名为心率、血氧、深睡或 REM；也不能把零/`FF` 换算为测量结果。更不能由这些占位模式断言戒指没有传感器、自动监测已关闭，或用户没有睡眠记录。

用户最初回答 G Band 已有睡眠图及体征，之后明确更正为新戒指尚未使用、没有睡眠图。应以最后的信息为准。本日志只能证明设备有响应，不能证明有有效的整夜记录；后续 SDK 实测也未取得睡眠。需要佩戴过夜生成记录后再验证分期。

## 与现有 App 代码对照

`sleeptongshu/BandScanner.swift` 的 `BLEStandardAccess` 目前仅允许以下标准特征：

| 服务 / 特征 | 用途 |
| --- | --- |
| `180F / 2A19` | 标准电量 |
| `180A / 2A24` | 标准设备型号 |
| `180D / 2A37` | 标准实时心率 |

服务发现会列出私有特征，但现有代码不会向其写入命令，也不会订阅私有通知。没有 `DF` 分包接收器、厂商认证状态机或历史睡眠适配器。因此，即使戒指在私有协议中有有效记录，当前 App 也无法将它们读入本地睡眠数据库。标准特征是否存在，仍要看这枚戒指的实际服务诊断，不能从本日志推断。

本次没有将日志中的命令原样重放给戒指。初始化序列可能包含校时、个人资料、开关或其他设置；不能将整段 SEND 序列视为无副作用的读取脚本。

## 官方接口核对

核对来源为 [Veepoo iOS SDK](https://github.com/HBandSDK/iOS_Ble_SDK)、[英文 API](https://github.com/HBandSDK/iOS_Ble_SDK/blob/master/iOS_sdk_source/doc/VeepooSDK%20iOS%20Api_en.md)，以及仓库 `iOS_sdk_source/Framework/2.2.XX.15/VeepooBleSDK.framework/Headers/` 中的公开头文件。

- `VPPeripheralModel.h` 明确描述 `A7` 设备功能数据和 `B8` 开关数据，提供 `sleepType`、`deviceVersion`、`deviceTestVersion` 等属性。这是比单凭产品销售名称更具体的协议线索。
- `VPBleCentralManage.h` 提供连接、密码验证与状态回调。其说明指出发现服务后会自动发送设备密码，并同步手机时间。设备验证与小米账号登录不是同一件事；日志不包含 SDK 的验证状态回调，不能据此宣称无需设备验证。
- `VPPeripheralBaseManage.h` 提供 `veepooSdkStartReadDeviceAllDataWithReadStateChangeBlock:`，以及按天读取睡眠的 `veepooSDK_readSleepDataWithDayNumber:result:`。后者对睡眠的日期编号要求是 `1...saveDays`，不能直接套用计步数据的 `0 = 今天` 规则。
- 普通睡眠可通过 `VPDataBaseOperation` 读取；精准睡眠使用 `VPAccurateSleepModel`。应先检查设备声明的睡眠类型，再决定分期映射，不能为普通睡眠补出 REM。
- SDK 文档说明内部数据接口不支持并发操作，并提醒避免多 App 同时操作同一设备。实际测试应先结束 G Band 的同步，串行执行验证和读取；无需先解绑或恢复出厂设置。

公开 API 说明如何使用 SDK，并未给出本日志全部原始标签的逐字节协议定义。因此本次没有自行猜测实现临床指标解析，也没有把 SDK 二进制加入项目后宣称已适配成功。

### SDK 二进制初步检查

已在本地研究目录下载上述 `2.2.XX.15` 目录中的库。实际文件大小为 14,103,744 字节，使用 `git hash-object` 核对，结果与官方仓库该文件的 blob ID `a775b2b84013c9d373fb02ed272977e7beae25bb` 一致。

`file`、`lipo` 和 `otool` 检查表明它是 arm64 静态 archive，目标带 `LC_VERSION_MIN_IPHONEOS`，不是可直接用于 iOS Simulator / Mac Catalyst 的多平台 XCFramework。接入时需将设备专用依赖与项目现有的模拟器、Catalyst 构建隔离。

官方示例的 Podfile 使用 FMDB、MJExtension，工程还链接 GRDFUSDK、JL_BLEKit、DFUnits、ZipZap、JLDialUnit、ABParTool 等库。符号检查也发现该 archive 引用了自身未定义的 `FMDatabaseQueue`、`GRDFUTool`、`JL_Assist`、`ZZArchive` 等外部类。具体哪些依赖必须随睡眠读取路径链接，仍需实际集成构建确认；不能只复制一个 framework 就认定完成接入。本次未向 App 引入这些二进制或改变签名配置。

## 直接同步需要完成的步骤

1. 用 sleeptongshu 连接戒指，在“监测与设备 → 穿戴设备 → 设备诊断 → 分享设备诊断”取得服务/特征 UUID、属性和实际错误，与本次载荷日志配对。此操作读取的是诊断信息，不需要抹除记录。
2. 验证官方 SDK 对 L03 Ultra / `00.12.11.00-2511` 的支持、二进制平台及依赖，先做真实 iPhone 的连接与验证回调检查；模拟器能编译不能代替硬件兼容验证。
3. 通过厂商接口串行同步历史，在完成回调后提取睡眠和可用体征。没有记录、验证失败、超时和未支持的功能需分别呈现。
4. 将厂商模型转换成现有 `SleepPayload`，保留来源、时间、缺失值，按设备和夜晚去重，再保存到本地 SwiftData。仅对实际睡眠区间内的有效体征计算夜间平均值。
5. 与 G Band 同一晚的入睡、起床、分期及体征逐项对照。验证通过后才能标记该型号支持；这次日志分析不能替代这一验收。

后续已开始 SDK 读取路径测试。G Band 是否向 Apple 健康写入睡眠仍需实际确认，不能将其他 Veepoo App 的功能当成 G Band 的能力。
